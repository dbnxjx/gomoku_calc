# ONNX 量化模型初测

## 结论

现有 uint8 ONNX 的策略输出与 FP32 不完全一致：104 个局面中，策略头 0 的最高分落点有 7 个不同，6 个差异局面里 FP32 第一、第二名的分差小于 0.1。整体 softmax 策略概率平均绝对差为 `0.000396`，值概率平均绝对差为 `0.000247`。差异主要体现在少数落点排序和原始输出值上，不能视为逐点等价。

uint8 文件体积最小，但本机 CPU 推理速度明显更慢，因此暂不建议使用这版 uint8。FP16 与 FP32 几乎一致，策略最高分落点在所有局面和六个策略头上都相同；本机速度也基本持平。

## 测试方法

- 从 KataGo 的 V7 Renju 特征生成器构造 26 盘合法开局；黑方首手在中心，其后随机选择邻近空点，并检查禁手。每盘取第 3、5、7、9 手后的局面，共 104 个局面。
- 使用同一份输入对比 `fp32.onnx`、`fp16.onnx`、`uint8.onnx`。输入为 22 个空间特征和 19 个全局特征，禁手特征开启；每种模型以 batch=1 和 batch=8 预热后计时。
- 运行环境为 Windows x64、ONNX Runtime 1.28.0、8 个 CPU 推理线程，执行 provider 为 `CPUExecutionProvider`。这里的速度是完整网络前向推理吞吐 `NN eval/s`，不是 KataGo 搜索的 `MCTS visits/s`。

## 结果

| 模型 | 文件大小 | batch=1 NN eval/s | batch=8 NN eval/s | 策略头 0 落点一致率 | 六个策略头一致率 | 策略概率 MAE | 值概率 MAE |
|---|---:|---:|---:|---:|---:|---:|---:|
| FP32 | 293.1 MB | 5.20 | 7.09 | 基准 | 基准 | - | - |
| FP16 | 147.0 MB | 5.33 | 6.99 | 100% | 100% | 0.00000390 | 0.00000781 |
| uint8 | 75.2 MB | 3.02 | 3.48 | 93.3% | 89.4% | 0.000396 | 0.000247 |

与 FP32 相比，uint8 在 7/104 个局面的策略头 0 首选落点不同；其中 6 个局面的 FP32 第一、第二名分差小于 0.1，另 1 个为 0.163。uint8 的原始策略输出 MAE 为 0.129、P99 绝对误差为 0.450；原始值输出 MAE 为 0.311。概率误差较小，但有少数首选落点会改变。

FP16 的原始策略输出 MAE 为 0.00113，原始值输出 MAE 为 0.00286。FP16 文件约为 FP32 的一半，CPU 上 batch=1 速度快约 2.5%，batch=8 慢约 1.5%，差别不足以说明有稳定加速。

## 适用范围

本次测到的是现有三份 ONNX 之间的相对差异。它们与目录中的 `zhizi_renju28b_s1600.bin.gz` 不是同一份权重：`.bin.gz` 内部标识为 `zhizigo_renju28b-b28c512nbt-s1617930240-d2051476833`，而 ONNX 文件名标识为 `kata1-b28c512nbt-s12043015936-d5616446734`；按张量布局转换后，首层卷积权重最大绝对差为 3.745。因此这些结果不能代表该 Renju `.bin.gz` 模型量化后的误差。

本机没有用于此次运行的 Android GPU/NPU provider，CPU 上的速度不能预测 Android 加速效果。KataGo 目前也没有加载这些 ONNX 的后端，所以这里无法得到 MCTS visits/s 或实战搜索强度。若要评估目标 Renju 权重，需要先从与 `.bin.gz` 相同的 checkpoint 导出 FP32 ONNX，再基于该文件生成量化版并重测。

复跑脚本为 `compare_onnx_quantization.py`；本次输入局面与机器可读结果分别保存在 `onnx_eval_inputs.bin`、`onnx_eval_positions.csv` 和 `onnx_quantization_results.json`。
